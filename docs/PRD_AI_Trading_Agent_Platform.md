> **项目代号：** TradeAgent-Veritas
> **版本：** v1.1 Draft（数据源调整版）
> **日期：** 2026-06-22
> **作者：** 产品经理 & 技术架构
>
> **v1.1 变更说明：** 由于无法获取真实 tick-by-tick 数据，新增 Tick 合成器模块，将 AKShare 免费分钟 K 线反向生成逐笔事件喂入撮合引擎。所有数据源调整为免费公开源。

## 一、项目背景与动机

### 1.1 行业痛点

当前 AI 交易 Agent 领域存在一个根本性问题：**决策验证不可信**。

以 TradingAgents（88k stars）为代表的开源框架解决了"Agent 该不该买"的问题，但其回测环境存在致命缺陷：

| 问题 | 说明 |
|------|------|
| 假设全部成交 | 订单以当前价格 100% 成交，不考虑真实市场深度 |
| 无订单簿语义 | 没有价格优先/时间优先、集合竞价、部分成交 |
| 无撤单逻辑 | 无法模拟撤单时机对策略的影响 |
| 无延迟模拟 | 忽略了排队等待和撮合延迟对策略的影响 |

**结果：** Agent 在回测中表现良好，实盘却大相径庭。策略研发者无法信任回测结果。

### 1.2 我们的解决方案

利用已有的 C++17 低延迟 A 股撮合引擎（RTAuction）作为**高保真仿真内核**，构建一个 AI 交易策略验证平台。

**核心差异：**

| 维度 | TradingAgents | 本项目 |
|------|--------------|--------|
| 回测引擎 | 假设成交 | **真实 OrderBook 撮合（0.002ms）** |
| 数据粒度 | 日线（Yahoo Finance） | **合成逐笔行情（从分钟线生成）** |
| 订单类型 | 市价单 | **限价单、撤单、集合竞价** |
| 成交逻辑 | `price = current_price` | **价格优先/时间优先，部分成交** |
| 验证保真度 | 低 | **高（微观结构级别）** |

**数据约束说明：** 本项目不依赖付费 Level 2 tick 数据。通过 Tick 合成器将免费分钟 K 线（AKShare）反向生成逐笔事件序列，喂入撮合引擎实现高保真仿真。合成 tick 保持了完整的订单簿语义（限价单排队、部分成交、撤单、集合竞价），回测保真度远高于简单假设成交。

### 1.3 项目定位

> **一句话：** AI 交易策略的高保真验证平台。
>
> **对比定位：** TradingAgents 解决"Agent 该不该买"，我们解决"Agent 买了之后会发生什么"。

## 二、目标用户与使用场景

### 2.1 目标用户

| 用户角色 | 需求 | 使用方式 |
|----------|------|----------|
| **量化策略研发者** | 验证 AI 策略在真实市场微观结构中的表现 | 上传策略 → 回测 → 查看绩效报告 |
| **AI Agent 研究者** | 测试 Agent 在金融场景中的决策质量 | 配置 Agent → 跑仿真 → 分析决策链路 |
| **面试官（间接）** | 评估候选人的系统设计和 AI 能力 | 看项目 Demo 和架构设计 |

### 2.2 核心使用场景

**场景一：策略回测验证**

```
用户：我想测试一个基于技术分析的 AI 交易策略在贵州茅台过去 30 天的表现。

操作流程：
1. 选择标的：贵州茅台（600519）
2. 选择时间范围：2026-05-01 ~ 2026-05-30
3. 配置 Agent：选择技术面分析师 + 策略决策 Agent
4. 启动回测
5. 查看结果：收益率、夏普比率、最大回撤、每笔交易明细
```

**场景二：多 Agent 协作决策**

```
用户：我想看多 Agent 辩论后决策的效果，和单 Agent 决策对比。

操作流程：
1. 配置方案 A：单个技术面 Agent
2. 配置方案 B：4 个分析师 + 多轮辩论 + 风控审批
3. 同一标的、同一时间段，跑两个方案
4. 对比结果：决策质量、风险控制、收益表现
```

**场景三：风控机制验证**

```
用户：我想验证三层风控在极端行情下的表现。

操作流程：
1. 选择 2026 年某次大跌行情
2. 配置激进策略（高仓位、无止损）
3. 观察风控系统如何拦截风险操作
4. 查看风控日志：哪些订单被拦截、原因、时间
```

### 3.2 核心设计：两本 OrderBook + Tick 合成器

这是整个项目最关键的架构决策：

**数据来源：** AKShare 免费分钟 K 线 → Tick 合成器 → 合成逐笔事件 → 喂入撮合引擎

```
┌─────────────────────────────────────────────────────────────┐
│                    回放主循环                                  │
│                                                             │
│   // 前置：Tick 合成器将分钟 K 线转为逐笔事件序列              │
│   tick_events = TickSynthesizer(akshare_minute_data)        │
│                                                             │
│   while (tick_events 还有事件) {                             │
│       ┌─────────────────────────────────────┐              │
│       │ Step 1: 喂合成历史事件                │              │
│       │                                     │              │
│       │   event = tick_events.Next()        │              │
│       │   engine_A.OnOrderData(event)  ←── 只回放历史       │
│       │   engine_B.OnOrderData(event)  ←── 历史 + Agent     │
│       └─────────────────────────────────────┘              │
│                                                             │
│       ┌─────────────────────────────────────┐              │
│       │ Step 2: 等待引擎排空                  │              │
│       │                                     │              │
│       │   WaitForDrain(engine_A)            │              │
│       │   WaitForDrain(engine_B)            │              │
│       └─────────────────────────────────────┘              │
│                                                             │
│       ┌─────────────────────────────────────┐              │
│       │ Step 3: Agent 观察市场状态            │              │
│       │                                     │              │
│       │   snapshot = engine_A.GetSnapshot() │              │
│       │   // Agent 看到的是真实历史市场       │              │
│       └─────────────────────────────────────┘              │
│                                                             │
│       ┌─────────────────────────────────────┐              │
│       │ Step 4: Agent 决策 + 风控            │              │
│       │                                     │              │
│       │   decision = agent.Decide(snapshot) │              │
│       │   approved = risk.Check(decision)   │              │
│       └─────────────────────────────────────┘              │
│                                                             │
│       ┌─────────────────────────────────────┐              │
│       │ Step 5: Agent 订单注入               │              │
│       │                                     │              │
│       │   if (approved) {                   │              │
│       │       engine_B.OnOrderData(order)   │              │
│       │       // Agent 订单进入仿真撮合      │              │
│       │   }                                 │              │
│       └─────────────────────────────────────┘              │
│   }                                                         │
│                                                             │
│   ┌─────────────────────────────────────┐                  │
│   │ Step 6: 绩效统计                     │                  │
│   │                                     │                  │
│   │   trades = engine_B.GetAgentTrades()│                  │
│   │   pnl = CalculatePnL(trades)        │                  │
│   │   report = GenerateReport(pnl)      │                  │
│   └─────────────────────────────────────┘                  │
└─────────────────────────────────────────────────────────────┘
```

**为什么需要两本 OrderBook？**

| 实例 | 输入 | OrderBook 状态 | 用途 |
|------|------|---------------|------|
| 实例 A | 只有历史事件 | 真实历史 | Agent 观察市场状态 |
| 实例 B | 历史事件 + Agent 订单 | 包含 Agent 影响 | Agent 订单撮合、绩效统计 |

如果只用一本 OrderBook，Agent 的订单会改变市场状态，导致后续历史事件的撮合结果偏离真实历史——回测就失去意义了。

### 4.2 各 Agent 详细设计

#### 4.2.1 TechnicalAnalyst（技术面分析师）

| 属性 | 说明 |
|------|------|
| **输入** | MarketSnapshot（10 档深度）、最近 N 笔成交、历史 K 线 |
| **分析维度** | MACD、RSI、KDJ、布林带、成交量、均线系统 |
| **输出** | `TechnicalReport{trend, signal, confidence, indicators}` |
| **LLM** | DeepSeek / Qwen（快速推理） |
| **Prompt 要点** | 给定当前市场数据，计算技术指标，判断趋势方向和强度 |

#### 4.2.2 FundamentalAnalyst（基本面分析师）

| 属性 | 说明 |
|------|------|
| **输入** | 公司财报数据、PE/PB/ROE、行业对比 |
| **数据源** | AKShare（财务数据）、Tushare（基本面指标） |
| **输出** | `FundamentalReport{valuation, quality, growth, risk_factors}` |
| **LLM** | DeepSeek / Qwen |
| **Prompt 要点** | 分析公司财务健康度、估值合理性、成长性 |

#### 4.2.3 SentimentAnalyst（情绪面分析师）

| 属性 | 说明 |
|------|------|
| **输入** | 资金流向、龙虎榜、大单统计、换手率 |
| **数据源** | AKShare（资金流向、龙虎榜） |
| **输出** | `SentimentReport{money_flow, institutional_activity, retail_sentiment}` |
| **LLM** | DeepSeek / Qwen |
| **Prompt 要点** | 分析主力资金动向、机构行为、散户情绪 |

#### 4.2.4 NewsAnalyst（新闻分析师）

| 属性 | 说明 |
|------|------|
| **输入** | 公司公告、行业新闻、政策动态 |
| **数据源** | AKShare（新闻）、网络爬取（可选） |
| **输出** | `NewsReport{events, impact, sentiment_score}` |
| **LLM** | DeepSeek / Qwen |
| **Prompt 要点** | 识别关键事件，评估对股价的影响方向和程度 |

#### 4.2.5 BullResearcher & BearResearcher（看多/看空研究员）

| 属性 | 说明 |
|------|------|
| **输入** | 4 份分析师报告 |
| **机制** | 多轮辩论（默认 2 轮，可配置） |
| **输出** | `DebateConclusion{bull_argument, bear_argument, consensus, confidence}` |
| **LLM** | DeepSeek / Qwen（需要较强推理能力） |
| **Prompt 要点** | 看多研究员寻找买入理由，看空研究员寻找卖出理由，互相质疑对方论据 |

**辩论流程：**

```
Round 1:
  Bull: "基本面强劲，PE 低于行业均值，技术面出现金叉"
  Bear: "但资金连续 3 天净流出，且已接近压力位"

Round 2:
  Bull: "资金流出是短期获利了结，中长期逻辑不变"
  Bear: "短期风险不可忽视，建议等回调再介入"

Consensus: 中性偏多，建议小仓位试探性买入
```

#### 4.2.6 TraderAgent（交易员）

| 属性 | 说明 |
|------|------|
| **输入** | 辩论结论 + 当前 MarketSnapshot + Agent 持仓状态 |
| **输出** | `OrderDecision{side, price, volume, order_type, confidence, reason}` |
| **LLM** | DeepSeek / Qwen（需要结构化输出） |
| **Prompt 要点** | 综合所有信息，输出具体交易决策（买/卖/持有），包含价格、数量、理由 |

**输出结构：**

```json
{
  "action": "BUY",
  "security_id": "600519",
  "price": 1800.50,
  "volume": 100,
  "order_type": "LIMIT",
  "confidence": 0.75,
```

| 属性 | 说明 |

### 5.2 Tick 合成器（核心创新模块）

由于无法获取真实逐笔行情数据，本项目设计了 Tick 合成器，将免费分钟 K 线反向生成逐笔事件序列，喂入撮合引擎实现高保真仿真。

**合成器设计：**

```
┌─────────────────────────────────────────────────────────────┐
│                    Tick 合成器                                │
│                                                             │
│  输入：AKShare 1 分钟 K 线                                   │
│  {open, high, low, close, volume, timestamp}               │
│                                                             │
│  ┌─────────────────────────────────────────────┐           │
│  │ Step 1: 价格路径生成                          │           │
│  │                                             │           │
│  │  约束：路径必须经过 Open → High/Low → Close  │           │
│  │  方法：布朗运动 + 几何布朗运动约束            │           │
│  │  输出：该分钟内每秒的价格序列                  │           │
│  └─────────────────────────────────────────────┘           │
│                         ↓                                   │
│  ┌─────────────────────────────────────────────┐           │
│  │ Step 2: 订单事件生成                          │           │
│  │                                             │           │
│  │  在每个价格点生成 ADD 事件（挂单）             │           │
│  │  根据价格趋势判断方向：                       │           │
│  │    上涨 → 买方 ADD > 卖方 ADD                │           │
│  │    下跌 → 卖方 ADD > 买方 ADD                │           │
│  │  根据 Volume 分配每个事件的成交量              │           │
│  │  随机插入 CANCEL 事件（模拟撤单）             │           │
│  └─────────────────────────────────────────────┘           │
│                         ↓                                   │
│  ┌─────────────────────────────────────────────┐           │
│  │ Step 3: 成交事件生成                          │           │
│  │                                             │           │
│  │  当买一 ≥ 卖一时生成 MATCH 事件              │           │
│  │  成交量从该分钟 Volume 总量中分配             │           │
│  │  成交价 = 买一/卖一的交叉价                   │           │
│  └─────────────────────────────────────────────┘           │
│                         ↓                                   │
│  ┌─────────────────────────────────────────────┐           │
│  │ Step 4: 事件排序 + 格式对齐                   │           │
│  │                                             │           │
│  │  按时间戳排序，保证因果关系                   │           │
│  │  输出格式兼容 RTAuction OrderData/TradeData  │           │
│  │  生成 10 档 MarketSnapshot（每分钟边界）      │           │
│  └─────────────────────────────────────────────┘           │
│                                                             │
│  输出：合成逐笔事件序列                                      │
│  [OrderData, OrderData, TradeData, OrderData, ...]         │
└─────────────────────────────────────────────────────────────┘
```

**质量约束：**

| 约束 | 说明 |
|------|------|
| OHLCV 一致性 | 合成事件经过撮合引擎后，产生的 K 线应与原始分钟 K 线一致 |
| 价格边界 | 所有价格在 [Low, High] 范围内 |
| 成交量守恒 | 所有成交总量 = 该分钟 Volume |
| 时间因果 | 事件时间戳严格递增 |
| 方向合理性 | 上涨分钟主动买 > 主动卖，下跌分钟相反 |
| 深度合理性 | 10 档买卖盘价格在 [Low, High] 区间合理分布 |

### 5.3 Python ↔ C++ 通信方案

当前撮合引擎没有 Python 绑定，需要新增通信层。

**推荐方案：gRPC**

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **gRPC** | 跨语言、高性能、接口定义清晰 | 需要维护 .proto 文件 | ⭐⭐⭐⭐⭐ |
| pybind11 | 性能最好、直接调用 C++ | 编译复杂、平台相关 | ⭐⭐⭐ |
| 共享内存 | 延迟最低 | 实现复杂、调试困难 | ⭐⭐ |
| 文件交换 | 实现最简单 | 延迟高、不适合实时 | ⭐ |

**gRPC 接口定义（草案）：**

```protobuf
service MatchingEngineService {
  // 喂入历史事件
  rpc FeedOrderEvent(OrderEvent) returns (EventResult);
  rpc FeedTradeEvent(TradeEvent) returns (EventResult);

  // Agent 订单操作
  rpc SubmitAgentOrder(AgentOrder) returns (OrderResult);
  rpc CancelAgentOrder(CancelRequest) returns (CancelResult);

  // 市场状态查询
  rpc GetMarketSnapshot(SnapshotRequest) returns (MarketSnapshot);
  rpc GetAgentTrades(TradeQuery) returns (TradeList);

  // 引擎控制
  rpc WaitForDrain(DrainRequest) returns (DrainResult);
  rpc GetEngineStatus(StatusRequest) returns (EngineStatus);
}
```

## 八、关键设计决策记录

### 8.0 为什么用合成 Tick 数据而不是真实 Tick？

| 方案 | 问题 |
|------|------|
| 真实 Tick 数据 | 需要券商 Level 2 权限或付费数据源，个人项目无法获取 |
| 日线/分钟线直接回测 | 不需要撮合引擎，Backtrader 就够了，项目失去差异点 |
| **合成 Tick 数据** | 免费（AKShare 分钟线）+ 保持撮合引擎完整能力（订单簿、部分成交、撤单、集合竞价） |

**合成 Tick 的价值：**
- 不依赖付费数据源，项目可独立复现
- 合成事件经过撮合引擎后产生的 K 线与原始分钟 K 线一致（质量可控）
- 保持了撮合引擎的完整订单簿语义，回测保真度远高于简单假设成交
- 面试时展示了"没有数据就创造数据"的解决问题能力

### 8.1 为什么用两本 OrderBook 而不是一本？

| 方案 | 问题 |
|------|------|
| 一本 OrderBook | Agent 订单改变市场状态 → 后续历史事件撮合偏离真实 → 回测失真 |
| **两本 OrderBook** | A 看真实历史，B 跑 Agent 仿真 → 互不干扰 → 回测可信 |

### 8.2 为什么风控用规则引擎而不是 LLM？

| 方案 | 问题 |
|------|------|
| LLM 做风控 | LLM 输出有概率性，可能漏判、误判 → 风控失效 |
| **规则引擎** | 确定性输出，100% 可靠 → 风控可信 |

LLM 适合做分析和决策（概率性任务），风控是确定性任务，必须用代码实现。

### 8.3 为什么用 gRPC 而不是 pybind11？

| 方案 | 问题 |
|------|------|
| pybind11 | 编译链复杂、平台相关、Windows 支持差 |
| **gRPC** | 跨语言、跨平台、接口定义清晰、性能足够 |

撮合引擎运行在 C++ 进程，Agent 运行在 Python 进程，gRPC 是最成熟的跨进程通信方案。

### 8.4 为什么选 DeepSeek / Qwen 而不是 GPT-4？

| 方案 | 问题 |
|------|------|
| GPT-4 | 成本高、中文金融场景不一定最优 |
| **DeepSeek / Qwen** | 中文能力强、成本低、可本地部署 |
